## 2. 预算的分配依据

- **model 层 290 行**：5 个文件承载 6 个领域对象（证书/续期/部署/通知/规则/审计）+ 枚举 + 校验，纯数据无 IO，行数天然可控；
- **store 层 465 行**：5 个仓储 + 迁移执行器；SQL 直接写在 Go 字符串常量里（内嵌迁移），不额外引入 ORM；
- **service 层 460 行**：业务规则与状态机集中地，是全项目核心，行数最多；
- **task 层 265 行**：调度器 + 5 个任务；任务逻辑薄，重活都在 service；
- **api 层 460 行**：5 个 handler 文件；每个 Handler 平均 ~20 行（解析 → 调 service → 封装响应）；
- **tlsutil 75 行**：3 个纯函数。

> 各文件预估含空行与包级注释；实现完成后若实测偏离，优先调整注释与辅助函数数量，而非改变分层。

## 5. 实现注意事项（保证预算可达）

1. **先搭骨架再填肉**：按上表顺序创建 24 个文件，每个文件先写结构声明与注释，再补实现，避免"写超了再拆文件"；
2. **SQL 集中**：所有 SQL 语句写在对应 store 文件的包级常量中，禁止散落；
3. **Handler 瘦身**：handler 只做「解码 → 校验参数 → 调 service → 写响应」，业务逻辑绝不进 handler，防止 api 层膨胀；
4. **注释即预算**：包注释、关键函数注释、状态机注释是行数的自然来源，也是文档要求的一部分；
5. **每个文件行数上限自检**：超过预估 ±20 行即暂停，检查是否放错了层；
6. **最终校验**：`bash scripts/count_lines.sh` + `go vet ./...` + `gofmt -l .` + `go test ./...` 全绿后才算完成。
