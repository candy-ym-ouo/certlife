# 01 · 需求与业务逻辑

## 1. 背景与目标

企业环境中 TLS/SSL 证书数量多、来源杂（自签、内部 CA、公共 CA），手工维护经常出现：
证书悄悄过期导致线上事故、续期后忘记部署新证书、部署后新证书未生效却无人发现、告警淹没无人处理。

CertLife 的目标是把证书的"登记 → 监控 → 续期 → 部署 → 验证 → 通知"全流程自动化，让运维与开发
在一个服务里看到每张证书的完整生命周期，并在任何环节失败时第一时间收到明确通知。

## 2. 用户角色

| 角色 | 能力 |
|------|------|
| 管理员（admin） | 全部权限：管理证书、部署目标、通知规则、手动触发任务、查看审计日志 |
| 运维/开发（operator） | 证书登记与查看、手动续期、查看部署与通知记录（不含删除与规则配置，MVP 阶段可合并为同一权限） |

MVP 阶段不引入完整 RBAC，仅通过 `X-API-Key` 做单密钥鉴权；文档保留角色概念以便后续扩展。

## 3. 功能需求

### 3.1 证书登记（证书元信息）

- 登记字段：
  - 基础：`name`（显示名）、`domain`（主域名）、`sans`（附加域名列表）、`issuer`、`serial_number`、`algorithm`（RSA/ECDSA）、`key_bits`
  - 有效期：`valid_from`、`valid_until`（UTC，`RFC3339`）
  - 归属：`owner`、`environment`（prod/staging/dev）、`tags`
  - 告警：`contacts`（接收通知的邮箱）、`notify_threshold_days`（提前 N 天告警，默认 30）
  - 续期：`auto_renew`（是否自动续期）、`renew_threshold_days`（剩余 N 天触发自动续期，默认 14）
  - 部署：`deploy_target_ids`（关联的部署目标）
- 登记时自动计算 `days_to_expire = valid_until - now`，并依据阈值初始化状态。
- 同一 `domain` 允许重复登记（可能多张证书轮换），但列表页会提示重复。
- 支持编辑与删除；删除为软删除（`deleted_at` 置位，审计留痕），防止误删后无法追溯。

### 3.2 到期检查

- 后台任务 `expiry_checker` 周期性扫描全部未删除证书：
  - `days_to_expire > notify_threshold` → 状态 `valid`；
  - `0 < days_to_expire <= notify_threshold` → 状态 `expiring_soon`；
  - `days_to_expire <= 0` → 状态 `expired`。
- 状态变化时：
  - 记录审计日志；
  - 对进入 `expiring_soon` / `expired` 的证书生成告警通知（受通知规则与去重约束）；
  - 更新 `last_checked_at`。
- 每次扫描输出统计：`scanned / valid / expiring_soon / expired / failed`。

### 3.3 续期任务

触发方式：
1. **自动**：`renewal_runner` 任务扫描 `auto_renew=true` 且 `days_to_expire <= renew_threshold_days` 且当前无进行中续期的证书；
2. **手动**：调用 `POST /api/v1/certificates/{id}/renew`（前端"立即续期"按钮），可带 `force=true` 忽略阈值。

续期流水线（状态机）：

```
pending → issuing → issued → deploying → verifying → completed
   │         │         │          │           │
   └─────────┴─────────┴──────────┴───────────┴→ failed（可重试回 pending）
```

- `pending`：已排队，等待签发；
- `issuing`：调用 `Issuer` 申请新证书（MVP 为 Mock 签发器，接口可替换为 ACME）；
- `issued`：新证书已签发，记录 `new_serial`，进入部署阶段；
- `deploying`：把新证书依次下发到该证书关联的部署目标；
- `verifying`：对每个部署目标执行 TLS 验证；
- `completed`：全部目标验证通过；
- `failed`：任一环节失败，记录 `error` 与 `attempt`，可重试（重置为 `pending`，`attempt+1`）。

业务规则：
- 同一证书同一时刻只允许一条进行中的续期（`pending/issuing/issued/deploying/verifying`），重复触发返回 409；
- 自动续期只对 `auto_renew=true` 的证书生效；
- 失败续期自动重试不超过 2 次（由 `renewal_runner` 处理），仍失败则产生失败通知；
- 每次续期生成一条 `Renewal` 记录，构成证书的续期历史。

### 3.4 部署验证

- 部署目标（`deployment_targets`）：`name`、`host:port`、`scheme`（https）、`method`（mvp 支持 `tls` 探测与 `static` 模拟下发）、`verify_tls=true`。
- 部署执行（`deployservice.Deploy`）：
  - `static` 方法：模拟下发（MVP 落盘到本地 `deployments/` 目录并按目标写入），返回部署记录；
  - `tls` 方法：仅登记目标信息，验证阶段做真实握手。
- 验证项（`tlsutil.Verify`）：
  1. TLS 握手成功（连接 `host:port`，校验服务器证书链）；
  2. 服务器证书序列号 == 新签发序列号（确认新证书已生效）；
  3. SAN 覆盖该证书声明的全部域名（`domain` + `sans`）；
  4. 服务器证书未过期（`valid_until > now`）；
  5. 指纹与签发记录一致（SHA-256）。
- 任一验证项失败 → 部署记录标记 `verification_failed`，续期标记失败；若配置了 `rollback_on_fail=true` 则执行回滚（静态方法下恢复旧证书文件），并记录审计日志。
- 全部通过 → 续期 `completed`，产生 `renewal_succeeded` 通知。

### 3.5 失败通知

通知事件类型（`EventType`）：

| 事件 | 触发场景 |
|------|----------|
| `expiring_soon` | 证书进入即将到期状态 |
| `expired` | 证书已过期 |
| `renewal_failed` | 续期流水线失败（含重试耗尽） |
| `verification_failed` | 部署验证失败 |
| `deploy_failed` | 部署执行失败 |
| `renewal_succeeded` | 续期+部署+验证全部成功 |
| `daily_summary` | 每日 09:00 汇总（不参与去重） |

通道与规则：
- 通道：`email`（SMTP）与 `webhook`（HTTP POST JSON）；
- 规则（`notification_rules`）：按 `event_types`、`environment` 匹配，指定通道与收件人/回调地址；规则可启停；
- 无匹配规则时静默丢弃，不产生通知记录（但审计日志保留事件）。

可靠性：
- 通知记录状态机：`pending → sent / failed`；`failed` 每轮由 `notify_dispatcher` 重试，最多 3 次，指数退避（1m/5m/30m）；
- 去重：同一证书同一事件类型 24 小时内只发一条（`daily_summary` 除外）；
- 发送结果（成功/失败/错误信息）写回通知记录，前端可查。

### 3.6 审计日志

- 记录动作：登记、更新、删除、状态变更、续期触发、续期结果、部署、验证、任务手动触发、规则变更；
- 字段：`actor`（API Key 名或 `system`）、`action`、`resource_type`、`resource_id`、`detail`（JSON）、`created_at`；
- 列表接口支持按资源与动作过滤。

### 3.7 统计与仪表盘

`GET /api/v1/stats` 聚合返回：
- 证书总数、按状态分布（valid/expiring_soon/expired）；
- 最近 7 天到期的证书列表；
- 30 天内即将到期数量；
- 续期成功率（近 30 天）、失败续期数；
- 今日通知发送数 / 失败数。

## 4. 领域模型与状态机汇总

### 4.1 证书状态

```
                    ┌─────────────────────────────┐
                    │  days_to_expire ≤ threshold  │
   valid ───────────┼────────────────────────────► expiring_soon
                    └─────────────────────────────┘
                    ┌─────────────────────────────┐
   expiring_soon ───┼─ days_to_expire ≤ 0 ───────► expired
                    └─────────────────────────────┘
   （任意状态） ───── 续期完成且新证书有效 ────────► valid（刷新为最新元信息）
```

状态仅由 `expiry_checker` 与续期完成动作推进，保证单一写路径。

### 4.2 续期状态机

```
       触发                签发成功              全部部署完成           全部验证通过
pending ────► issuing ──────────► issued ──────────► deploying ──────────► verifying ──► completed
   ▲             │                   │                   │                   │
   │             └── 签发失败 ───────┴─── 部署失败 ───────┴─── 验证失败 ─────┴─► failed
   └──────────────────────────── 重试（attempt+1）──────────────────────────────┘
```

## 5. 非功能需求

| 类别 | 要求 |
|------|------|
| 正确性 | 到期计算以 UTC 为准；状态推进单一写路径；续期串行（单证书并发保护） |
| 可靠性 | 后台任务崩溃可恢复（任务幂等：重复执行不产生重复续期/通知）；通知重试+去重 |
| 可观测 | `/api/v1/health` 健康检查；任务执行统计；审计日志 |
| 可维护 | 分层清晰（config/model/store/service/task/api）；迁移随启动自动执行 |
| 安全 | API Key 鉴权；Webhook 请求带签名头（`X-CertLife-Sign`，HMAC-SHA256）；日志脱敏（不记录私钥/凭据） |
| 约束 | Go 代码（不含测试）行数 ∈ (2000, 2200)，文件数 ∈ (20, 25)；前端保持"简单"（无构建步骤） |

## 6. 边界与后续扩展（本期不做）

- 真实 ACME/Let's Encrypt 签发（保留 `Issuer` 接口，后续实现 `acmeIssuer`）；
- 多用户 RBAC 与细粒度权限；
- 证书私钥安全托管（Vault 集成）；
- 多数据源证书自动发现（扫描 nginx/AWS ALB 等）；
- 本期仅 SQLite，后续可换 PostgreSQL（store 层接口隔离已预留）。

## 7. 关键业务规则清单（实现验收依据）

1. 登记证书时 `valid_from < valid_until`，否则 400；
2. 到期检查幂等：重复执行结果一致，仅产生一次状态变更与通知；
3. 自动续期只处理 `auto_renew=true` 且剩余天数 ≤ 阈值且无进行中续期的证书；
4. 单证书并发续期保护：已存在进行中续期时返回 409；
5. 续期失败自动重试 ≤ 2 次，之后发 `renewal_failed` 通知；
6. 验证必须覆盖：握手、序列号、SAN、有效期，四项全过才算完成；
7. 通知去重：同证书同事件 24h 内仅 1 条（`daily_summary` 除外）；失败重试 ≤ 3 次；
8. 所有写操作（登记/更新/删除/状态变更/续期/部署/规则）写审计日志；
9. 删除为软删除，`GET` 列表默认不返回已删除记录。
