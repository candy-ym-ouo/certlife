# 05 · 后台任务设计

## 1. 设计目标

- 覆盖业务四类定时工作：到期检查、续期执行、部署验证、通知派发（+每日日报）；
- 可手动触发（API），便于测试与端到端验证；
- 幂等：任务重复执行不产生重复续期、重复通知；
- 可观测：每次执行记录结果，可通过 `GET /api/v1/tasks` 查看；
- 优雅关闭：`SIGTERM` 时停止调度、等待当前轮次结束。

## 2. 调度器（internal/task/scheduler.go）

```go
type Job struct {
    Name     string
    Interval time.Duration
    Run      func(ctx context.Context) JobResult
}
type JobResult struct { OK bool; Detail string }
type Scheduler struct {
    mu    sync.Mutex
    jobs  map[string]*Job
    last  map[string]RunInfo   // last_run_at / result / error / runs
    wg    sync.WaitGroup
    stop  chan struct{}
    running map[string]bool    // 防重入
}
```

行为：
- `Register(job)`：注册任务（重复名称报错）；
- `Start(ctx)`：为每个任务启动一个 goroutine，用 `time.Ticker` 按 `Interval` 触发；首个周期立即执行一次（便于启动后快速自检）；
- `TriggerNow(name) (JobResult, error)`：同步手动触发；任务不存在 → `ErrTaskNotFound`；正在运行 → `ErrTaskRunning`；
- `防重入`：`running[name]` 为 true 时跳过本轮（并记录 `skipped`）；
- `Stop()`：关闭 stop 通道，`wg.Wait()` 等待在跑任务完成（带 30s 超时保护）。

## 3. 任务清单（internal/task/jobs.go）

### 3.1 expiry_checker（到期检查，默认每 6h）

1. 取全部未删除证书；
2. 对每张调用 `certservice.RefreshStatus(cert, now)`：
   - 重算 `days_to_expire`；
   - 若状态变化：更新 + 审计 `cert.status_changed`；
   - 新状态为 `expiring_soon` / `expired` → `notifyservice.Dispatch(event, cert)`；
3. 返回统计 `scanned=12 valid=8 expiring=3 expired=1`。

幂等性：状态未变则不更新、不通知；重复执行结果一致。

### 3.2 renewal_runner（续期执行，默认每 1h）

1. 自动续期：查自动续期候选（`auto_renew=1`、`days_to_expire <= renew_threshold_days`、无进行中续期）→ 逐个 `Trigger(auto)`；
2. 失败重试：查 `status='failed' AND attempt < 3` 的续期 → `RetryFailed`（重置 pending、attempt+1）；
3. 推进流水线：对 `pending/issuing/issued/deploying/verifying` 的续期调用 `renewalservice.RunPipeline`（见下）；
4. 返回统计 `auto_triggered=2 retried=1 completed=1 failed=0`。

> 说明：流水线也可由 `deploy_verifier` 推进；为避免双跑，规定**续期流水线（签发与状态推进）只由 renewal_runner 驱动**，`deploy_verifier` 只处理部署与验证的**重试**。

### 3.3 deploy_verifier（部署验证，默认每 30m）

1. 取 `deploying/verifying` 状态的续期；
2. 对部署失败的部署记录（`status='failed'` 且重试 < 3）重新 `deployservice.Deploy`；
3. 对 `verifying` 的续期执行 `deployservice.Verify`（调 tlsutil 真实握手）；
4. 全部目标通过 → 续期 `completed` + `renewal_succeeded` 通知；
5. 任一失败 → 续期 `failed` + `verification_failed`/`deploy_failed` 通知；`rollback_on_fail` 时回滚。

### 3.4 notify_dispatcher（通知派发，默认每 5m）

1. 取 `status='pending'` 或（`failed` 且 `retry_count < 3`）的通知，按 `created_at` 升序，每轮最多 50 条；
2. 逐条发送（SMTP / Webhook，带 HMAC 签名）；
3. 成功 → `sent`；失败 → `failed` + `retry_count+1` + `last_error`；
4. 重试退避：`1m / 5m / 30m`（依据 `retry_count`，未到时间不取）。

### 3.5 daily_summary（每日日报，默认每天 09:00 本地时区）

1. 聚合昨日+今日数据：证书总数、状态分布、近 7 天到期列表、续期成功/失败、通知发送统计；
2. 生成一条 `daily_summary` 通知（channel 取规则配置，跳过去重）；
3. 无规则时仅记审计。

## 4. 任务配置（config.yaml 片段）

```yaml
scheduler:
  expiry_checker_interval: 6h
  renewal_runner_interval: 1h
  deploy_verifier_interval: 30m
  notify_dispatcher_interval: 5m
  daily_summary_time: "09:00"
```

## 5. 手动触发与端到端验证

`POST /api/v1/tasks/run` 让验证脚本可以确定性驱动：

```bash
curl -s -X POST localhost:8080/api/v1/tasks/run -H "X-API-Key: dev-key" \
     -H "Content-Type: application/json" -d '{"name":"expiry_checker"}'
# → { "result":"ok", "detail":"scanned=1 valid=0 expiring=0 expired=1" }
```

`scripts/verify.sh` 的驱动顺序：登记 3 张测试证书（1 张 3 天后到期、1 张已过期、1 张正常）→
`expiry_checker` → 断言状态与通知 → `renewal_runner`（对可续期证书）→ `deploy_verifier` → 断言续期 completed、部署验证通过、`renewal_succeeded` 通知产生。

## 6. 错误与恢复

- 任务 panic：scheduler 用 `defer recover` 捕获，记录 `last_error`，任务继续下一轮；
- DB 短暂不可用：任务记录失败，下一轮重试；
- 崩溃恢复：所有业务数据（续期、通知、部署）均在 DB，任务幂等，重启后自然续跑。
